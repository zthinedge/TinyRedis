- 已经有主链路直觉

## 当前能力画像

### 1. 请求主链路理解

当前水平：`中等偏上`

已经能讲出的内容：

- 客户端命令会以 RESP 形式通过 TCP 字节流发到服务端
- 网络层读取数据后喂给 RESP 解析器
- 解析结果会转成 `RESPObject`
- 命令层再转成 argv 形式进行分发
- 存储层负责真正修改内存状态
- 响应通过 encoder 编码后写回发送缓冲区

已经体现出的优点：

- 对 `net -> protocol -> command -> storage -> response` 这条链路有正确方向感
- 已经不是“只会背模块名”，而是能说出大概的数据流

还存在的问题：

- 目前表达还偏概括，没法稳定落到具体文件和函数
- 对错误路径、事件循环调度、读写缓冲细节还没有真正吃透

建议继续锚定：

- `src/net/epollServer.cpp`
- `src/protocol/respParser.cpp`
- `src/command/commandDispatcher.cpp`
- `src/command/inMemoryDB.cpp`

### 2. AOF 理解

当前水平：`中等`

已经能讲出的内容：

- AOF 是持久化机制，解决内存断电丢数据问题
- AOF 主要记录写请求
- 服务重启时需要重新回放这些请求恢复状态
- 为了避免文件过大，需要 rewrite

已经体现出的优点：

- 对 AOF 的目标理解是正确的
- 能把“写命令持久化”和“重放恢复”联系起来
- 能意识到 rewrite 是为了收缩日志而不是简单复制文件

还存在的问题：

- 还没形成 AOF 四条链路的稳定模型：
  - `append`
  - `replay`
  - `rewrite`
  - `bgrewrite`
- 对失败语义和容错边界不熟
- 对 `always/everysec/no` 的差别还没有能结合代码讲清

当前状态结论：

- AOF 功能层面已收口
- 但表达层面还需要复习

建议复习方式：

- 不再继续扩功能
- 重点把 `aof.cpp` 和 `test_aof.cpp` 讲熟

### 3. Replication 理解

当前水平：`明显薄弱`

当前已表现出的理解：

- 知道主从复制是为了多保存一份数据
- 知道大方向上应该是主节点把数据发给从节点
- 知道通信底层依赖 socket

当前明显不会的点：

- 不知道 `master` 和 `replica` 在项目里各自负责什么
- 不知道为什么第一次同步必须先 `FULLRESYNC`
- 不知道全量同步和后续增量传播的区别
- 不知道当前项目里的主从复制到底已经做到哪一步

这是当前最主要的短板。

后续优先级应最高。

建议先只吃透下面 5 个点：

1. `replicaof` 配置启动后发生了什么
2. replica 如何主动连接 master
3. 为什么第一次要做全量同步
4. `FULLRESYNC` 后 master 发送的是什么
5. 后续新的写命令如何传播给 replica

建议复习入口：

- `src/net/epollServer.cpp`
- `include/replication/replicationState.hpp`
- `README.md` 里的 replication 描述

### 4. 工程能力表达

当前水平：`有雏形，但不稳定`

已经能提到的工程点：

- 模块解耦
- 每层只做自己的职责
- 单元测试
- CMake 项目管理
- 可以提到渐进式哈希这类底层实现点

问题不在于完全没有工程能力，而在于：

- 这些点目前还是“零散关键词”
- 还没有变成“能证明自己做过工程”的完整表达

后续需要把这些点组织成下面这种句式：

- 为什么这么拆模块
- 这样拆解决了什么问题
- 如何验证这个设计是可用的
- 当前实现与理想实现还有什么差距

## 目前最适合的复习顺序

### 第一阶段：先把已有东西讲成自己的语言

顺序：

1. 请求主链路
2. AOF 四条链路
3. Replication 基础模型

目标：

- 不追求扩功能
- 只追求“能稳定讲清”

### 第二阶段：专项补 replication

当前最值得继续深挖的模块就是复制。

最小目标：

- 能讲清当前复制主链路
- 能解释为什么现在只是“简化版”
- 能说出下一步想做什么：
  - backlog
  - partial resync
  - 断线重连继续同步

### 第三阶段：把项目讲法工程化

目标不是再写很多代码，而是形成可讲述材料：

- 项目目标
- 架构图
- 主链路
- 模块边界
- 测试与验证方式
- 已知不足与后续计划

## 当前最需要查漏补缺的问题

### 链路类

- `SET k v` 从 socket 到响应返回，具体经过哪些函数
- `CommandDispatcher` 在主链路里承担什么职责
- `InMemoryDB` 和命令层的边界是什么

### AOF 类

- `append / replay / rewrite / bgrewrite` 四条链路分别在做什么
- 为什么只记录写命令
- 尾部截断容错和格式损坏失败的边界是什么
- `everysec` 是如何依赖 `cron` 驱动刷盘的

### Replication 类

- 为什么 replica 第一次不能只收增量写命令
- `FULLRESYNC` 的作用是什么
- master 当前内存状态是如何转成命令流发给 replica 的
- master 收到新写命令后怎么广播给 replica

### 工程表达类

- 为什么要做模块拆分
- 为什么要做单元测试
- 当前测试覆盖了哪些能力
- 当前实现和 Redis 正版差在哪里

## 后续问答规则

后续继续问答时，优先按下面顺序推进：

1. 先问主链路
2. 再问 AOF
3. 最后问 replication

问答原则：

- 一次只追一个点
- 先追概念模型，再落到代码文件
- 优先让回答变成“自己的语言”，而不是背术语

## 阶段目标

当满足下面这些条件时，可以认为 `TinyRedis` 的复习进入下一阶段：

- 能独立讲清请求主链路
- 能独立讲清 AOF 四条链路
- 能独立讲清 replication 的第一次全量同步和后续传播
- 能说出自己实现与 Redis 正版的差距
- 能明确指出项目里最能体现工程能力的 3 个点

## 一句话总结

当前不是“没有工程能力”，而是：

`已经有链路感和模块感，但还没把它们沉淀成稳定的系统理解和工程表达。`

后续最值得投入的方向不是继续乱加功能，而是：

`把已有实现讲明白，尤其是 replication。`
